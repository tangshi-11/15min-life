# 实测对比报告：昆明市五华区翠湖片区

项目：15 分钟生活圈・智能体检与规划助手 ｜ 版本：2.0.0 ｜ 更新日期：2026-10-10

> 本版基于 **48 方向扇区采样 + 网格硬边界修正 + 单点算路复核（方案 B）** 口径重写，
> 并修正了早期报告/验证脚本的一处**坐标口径 bug**（见第 7 节），结论以本版为准。

## 1. 测试目的

验证系统对特定社区（昆明市五华区翠湖片区）的体检能力，重点回答三个问题：

1. 基于真实路网测时得到的「15 分钟步行等时圈」与传统「欧氏圆形半径」相比，差异有多大；
2. 等时圈内民生设施覆盖情况与综合评分；
3. 服务盲区（灰色区域）能否被准确识别。

**中心点**：25.0406°N, 102.7146°E（翠湖片区）｜**模式**：真实百度 API（live），无降级警告。

## 2. 测试方法与口径（2.0.0）

| 项目 | 说明 |
| --- | --- |
| 中心点 | 25.0406°N, 102.7146°E（翠湖片区），地址"昆明市五华区翠湖公园" |
| 步行时间阈值 | 15 分钟（可配置 10/15/20 分钟） |
| 等时圈算法 | **48 方向** × 100m 步长扇区采样（0~2km）→ 批量算路（routematrix 分块 + 限流）→ 边界插值 → **网格硬边界修正**（消除跨水/跨河插值凸出）→ IDW 60×60 → Marching Squares 等值线 |
| **单点复核（方案 B）** | 对均匀角度抽样 12 个方向，用轻量单点算路（directionlite）复核：真实耗时 >15 分钟 → 向内二分内缩；明显低于阈值 → 向外探测外扩（≤2 步）；复核失败（配额/异常）→ 保持原边界安全降级；复核后重建网格剖面使渲染与统计同步修正 |
| 坐标口径 | 后端边界多边形输出 **BD-09**；前端渲染时转换 WGS-84；验证脚本直接使用 BD-09（不再二次转换，见第 7 节） |
| 设施分类 | 医疗 / 教育 / 购物 / 养老 / 文体 / 餐饮 / 交通（11 类 POI 检索去重后归并） |
| 盲区规则 | 1km 内缺菜市场、药店、小学中任意一类 → 服务盲区 |

## 3. 等时圈 vs 圆形半径对比（live，2026-10-10）

| 指标 | 等时圈（真实测时） | 欧氏圆形（半径 = 最远可达） | 差异 |
| --- | --- | --- | --- |
| 面积 | **1.35–1.99 km²**（批次波动） | 以 max_reach 为半径 | 等时圈显著小于圆形 |
| 最远可达 | 929.5–1185.3 m | 同左（基准） | — |
| 边界点直线距离分布 | min=433m / p25=473m / median=1158m / p75=1174m / max=1185m，极差 752m | 理想圆极差应 ≈0 | 等时圈受真实路网约束，方向性差异显著 |
| 形状特征 | 非规则多边形，受路网/水域/过街条件约束收缩 | 理想圆形 | 等时圈更贴近真实生活体验 |

**结论**：道路并非直线——翠湖片区各方向 15 分钟可达距离差异明显（极差 752m，最远方向约为最近方向的 2.7 倍）。
若用圆形半径评估，会**高估可达面积**，这正是传统静态普查方法容易造成"服务盲区漏判"的原因。

* 盲区扣分：1 处盲区 × -5 = -5

**结论**：翠湖片区 15 分钟步行圈内医疗/餐饮/交通/购物/教育/文体覆盖良好，但**圈内无养老设施**是主要缺口；
另有 1 处服务盲区（缺菜市场/药店/小学），被系统自动标注为"灰色区域"。

## 6. 真实路网方向性复核（directionlite 单点抽样）

对等时圈边界按角度均匀取 5 个点，用百度单点步行算路（directionlite）复核真实耗时：

| 方位角 | 直线距离 | 直线耗时(1.2m/s) | 真实路径耗时 | 说明 |
| --- | --- | --- | --- | --- |
| 0.0° | 1175m | 979s | **1348s（22.5 分）** | 方向被批量口径高估（方案 B 复核生效时内缩） |
| 69.3° | 1185m | 988s | **1216s（20.3 分）** | 同上 |
| 139.9° | 559m | 466s | **706s（11.8 分）** | 方向被低估（复核生效时外扩） |
| 212.3° | 556m | 463s | **787s（13.1 分）** | 同上 |
| 283.7° | 460m | 383s | **676s（11.3 分）** | 同上 |

**发现**：
1. 批量算路（routematrix）与单点算路（directionlite）的步行耗时口径存在 ±25% 左右的方向性偏差
   （个别方向 batch 高估、个别低估），不是单一速度系数可校准——**这正是方案 B 逐方向复核的依据**；
2. 方案 B 复核生效时，边界整体收缩（max_reach 1185.3 → 929.5m，面积 1.99 → 1.35km²），
   证明复核逻辑确实在修正批量口径偏差；
3. **复核受百度日配额约束**：directionlite 与 routematrix 均为按 AK 计日的配额，连续多次
   验证会触发 status=302（天配额超限）/ 401（并发超限），此时复核自动降级为"保持原边界"
   （安全降级，不阻断主流程）——完整 5 点达标复验需在**配额恢复（次日）或提额后**执行。

## 7. 坐标口径修正说明（审计点）

早期报告与验证脚本曾对后端输出的边界多边形（已是 BD-09）**再次执行 wgs84→bd09 转换**，
导致抽样点坐标错位（数百米级），并错误得出"极差 1626m、湖面方向假覆盖严重"的结论。

- 已修正：`scripts/verify_real_road.py` 直接使用 BD-09 边界点做角度/距离/单点算路复核；
- 修正后真实极差 **752m**（仍证明方向性差异显著，但不存在"大面积跨湖假覆盖"）；
- 该修正属于**验证方法层面**的纠偏，产品代码本身口径正确（后端输出 BD-09、前端渲染转 WGS-84）。

## 8. 性能（live）

| 环节 | 耗时 |
| --- | --- |
| 批量测时（48 方向 × 20 点 = 960 点，分块请求） | ~20s（受百度 QPS 与配额重试影响，配额紧张时更长） |
| 单点复核（≤12 方向 × 数次） | ~10–30s（受 directionlite 配额/并发影响） |
| IDW + 等值线 + 盲区 + 报告 | <1s |
| 端到端（POST /api/inspect） | **~52–70s**（含批次波动） |

优化方向（正式版）：复核方向数、二分次数可配置（`refine_boundaries` 参数），
提额后可提升到全 48 方向复核，精度与耗时同步提升。

## 9. 局限与已知问题

* 等时圈精度受采样密度（48 方向 × 100m）限制，方向间细节由 IDW 插值近似；
* 批量算路与单点算路口径存在方向性偏差（±25% 量级），方案 B 复核对 12 个抽样方向校准，
  其余方向暂以批量口径为准；**完整校准需在百度提额后全方向复核**；
* 端到端耗时约 1 分钟，主要受百度 QPS/配额约束；配额耗尽时自动降级演示数据并在页面明示；
* 单次运行结果有轻微批次波动（面积 1.35–1.99 km²），源于真实路况逐次变化与复核降级状态差异。

## 10. 复现方式

```bash
# 1) 配置 .env（BAIDU_AK_SERVER=你的AK），启动服务
cd backend && .\.venv\Scripts\python.exe run.py
# 2) 跑真实路网方向性复核
python scripts/verify_real_road.py
# 3) 单元测试（含方案 B 复核逻辑）
cd backend && .\.venv\Scripts\python.exe -m pytest -q
```

> 说明：复核验证依赖百度日配额（routematrix 批量 + directionlite 单点），
> 配额耗尽时脚本/体检会自动降级（Mock 或保持原边界），请在配额充足时段复验。
